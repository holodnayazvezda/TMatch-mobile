# ADR: Архитектурные решения Tmatch

## Статус документа

Этот файл фиксирует архитектурные решения, наблюдаемые в текущем состоянии кодовой базы на 2026-03-16.

## Обзор системы

`Tmatch` это модульное Android-приложение на Kotlin, Jetpack Compose и Firebase Cloud Messaging. Кодовая база разделена на:

- `app`: точка входа приложения, корневая навигация, верхнеуровневая сборка DI-графа.
- `api/*`: стабильные контракты фич, включая доменные модели, gateway-интерфейсы и navigation key.
- `feature/*`: UI, ViewModel, use case и DI конкретных фич.
- `data/tmatch_api`: конкретные инфраструктурные реализации для работы с API и локальным хранением сессии.
- `common/ui`: общая дизайн-система, UI-компоненты, тема и общие экраны.

## ADR-001: Модульная структура с контрактными модулями

- Статус: Наблюдаемое/Действующее
- Контекст: Проект разделён на `api`, `feature`, `data` и `common` модули. Feature-модули зависят от контрактов из `api/*`, а `app` подключает конкретную реализацию данных.
- Решение: Использовать модульные границы, где контракты лежат в `api/*`, реализация фич в `feature/*`, а инфраструктурная реализация в `data/tmatch_api`.
- Последствия:
- Feature-модули отделены от деталей транспорта и хранения данных.
- `app` выступает как composition root и может подменять реализации без изменений в feature-коде.
- Навигационные ключи и доменные интерфейсы доступны без подтягивания экранов и инфраструктуры.
- Возможные альтернативы:
- Монолитный `app`-модуль. Плюсы: проще стартовать, меньше Gradle-конфигурации. Минусы: хуже масштабируемость, сильная связанность, сложнее выделять контракты.
- Разделение только на `feature` и `core`, без `api/*`. Плюсы: меньше модулей. Минусы: контракты и реализации смешиваются, сложнее подменять инфраструктуру и строить слабосвязанные зависимости.

## ADR-002: `app` является единственным composition root

- Статус: Наблюдаемое/Действующее
- Контекст: `TMatchApplication` запускает Koin и регистрирует data- и feature-модули в одном месте.
- Решение: Централизовать сборку графа зависимостей в модуле `app`.
- Последствия:
- Стартовая конфигурация зависимостей прозрачна и легко проверяется.
- Нижележащие модули не инициализируют себя самостоятельно.
- Конфигурация окружения, включая `API_BASE_URL` и debug-флаги, пробрасывается из `app`.
- Возможные альтернативы:
- Self-registration модулей. Плюсы: меньше кода в `app`. Минусы: сложнее понять полный граф, тяжелее контролировать порядок и окружение.
- Несколько composition root по feature boundary. Плюсы: выше автономность отдельных flow. Минусы: дублирование wiring и риск расхождения конфигурации.

## ADR-003: Внедрение зависимостей через Koin

- Статус: Наблюдаемое/Действующее
- Контекст: Основные зависимости и ViewModel создаются через Koin-модули.
- Решение: Использовать Koin как DI-контейнер вместо ручных фабрик или compile-time DI.
- Последствия:
- Регистрация модулей остаётся компактной и читаемой.
- ViewModel удобно получать из Compose.
- Корректность графа частично проверяется smoke-тестами, но в основном валидируется во время выполнения.
- Возможные альтернативы:
- Hilt/Dagger. Плюсы: compile-time валидация графа, сильная интеграция с Android. Минусы: выше порог входа, больше шаблонного кода, тяжелее быстрые изменения.
- Ручные фабрики. Плюсы: минимум магии, явный контроль зависимостей. Минусы: быстро растёт объём boilerplate, сложнее поддерживать на масштабе.

## ADR-004: UI полностью на Jetpack Compose

- Статус: Наблюдаемое/Действующее
- Контекст: Приложение использует Compose во всех фичах, Material 3 и общую тему из `common/ui`.
- Решение: Строить UI полностью на Jetpack Compose с общей дизайн-системой в отдельном модуле.
- Последствия:
- Фичи используют единый визуальный язык и общие компоненты.
- Тема, контролы и общие экраны переиспользуются без дублирования.
- Проект не разделён между XML и Compose-подходами.
- Возможные альтернативы:
- XML + Fragments. Плюсы: зрелая экосистема, много готовых паттернов. Минусы: больше шаблонного кода, слабее декларативность, сложнее единый state-driven UI.
- Гибрид XML и Compose. Плюсы: можно мигрировать постепенно. Минусы: архитектура становится смешанной, повышается стоимость сопровождения.

## ADR-005: Навигация на Navigation 3 с back stack под контролем `app`

- Статус: Наблюдаемое/Действующее
- Контекст: `app` хранит `SnapshotStateList<Any>` как back stack внутри `TMatchAppState` и передаёт его в feature-графы.
- Решение: Использовать `androidx.navigation3` с ручным управлением back stack на уровне приложения вместо fragment navigation или feature-owned navigator.
- Последствия:
- Навигационный поток полностью виден в одном месте.
- Фичи добавляют свои entry через `NavKey`-контракты.
- `app` напрямую контролирует tab navigation, auth reset и глобальные экраны через app-level coordinator state.
- Подход гибкий, но инварианты back stack поддерживаются соглашениями, а не строгой типизацией графа.
- Возможные альтернативы:
- Navigation Compose с `NavController`. Плюсы: стандартный путь, больше примеров и интеграций. Минусы: меньше прямого контроля над собственным стеком и сложнее нетиповые сценарии.
- Собственный navigator abstraction. Плюсы: полный контроль и типизация под свои нужды. Минусы: выше стоимость поддержки и больше инфраструктурного кода.

## ADR-006: Навигационные контракты фич живут в `api/*`

- Статус: Наблюдаемое/Действующее
- Контекст: Ключи навигации вроде `SignInNavKey`, `ProfileNavKey`, `MatchingNavKey` и `ChatsNavKey` опубликованы из API-модулей.
- Решение: Выносить навигационные контракты в контрактные модули, а не заставлять потребителей зависеть от feature-реализаций.
- Последствия:
- Межфичевая навигация опирается на стабильные контракты.
- `app` может оркестрировать flow, не раскрывая внутренности фич.
- Потребителям не нужен доступ к конкретным классам экранов.
- Возможные альтернативы:
- Держать `NavKey` внутри feature-модулей. Плюсы: всё рядом с реализацией. Минусы: межмодульная навигация начинает тянуть implementation dependency.
- Строковые route-имена. Плюсы: просто и привычно. Минусы: ниже type safety, выше риск ошибок при рефакторинге.

## ADR-007: Стартовый экран определяется по сессии и состоянию профиля

- Статус: Наблюдаемое/Действующее
- Контекст: `AppStartDestinationResolver` выбирает между onboarding, profile setup и основным экраном профиля на основе сохранённой сессии и доступности профиля на backend.
- Решение: Рассматривать аутентификацию и заполненность профиля как два отдельных измерения стартового состояния приложения.
- Последствия:
- Пользователь с активной сессией пропускает onboarding.
- Новый или незавершивший профиль пользователь попадает в profile setup.
- При отсутствии сети используется локально закэшированное состояние `profileCompleted`.
- Возможные альтернативы:
- Всегда спрашивать backend на старте и не использовать локальный fallback. Плюсы: одно истинное состояние. Минусы: хуже UX в офлайне и при деградации сети.
- Хранить один coarse-grained app state enum. Плюсы: проще модель. Минусы: сложнее выражать переходы и fallback-логику.

## ADR-008: Состояние сессии хранится безопасно

- Статус: Наблюдаемое/Действующее
- Контекст: `SharedPrefsAuthSessionStore` использует `EncryptedSharedPreferences` и `MasterKey`.
- Решение: Хранить токен сессии и флаг завершённости профиля в зашифрованном локальном хранилище.
- Последствия:
- Чувствительные данные не лежат в открытом виде в обычных SharedPreferences.
- После перезапуска приложения можно восстановить авторизацию без повторного входа.
- Уровень безопасности выше, чем у обычных prefs, при относительно простой реализации.
- Возможные альтернативы:
- Обычные SharedPreferences. Плюсы: проще и быстрее. Минусы: слабая защита секретов.
- AccountManager или внешний secure storage abstraction. Плюсы: потенциально сильнее изоляция. Минусы: выше сложность и интеграционные затраты.

## ADR-009: Сетевой слой на Ktor + OkHttp

- Статус: Наблюдаемое/Действующее
- Контекст: `data/tmatch_api` создаёт настроенный `HttpClient` с JSON-сериализацией, логированием, базовым URL и движком OkHttp.
- Решение: Стандартизовать сетевое взаимодействие через Ktor client с OkHttp на Android.
- Последствия:
- Все gateway используют единый HTTP-стек и единые правила сериализации.
- Транспортный слой легко тестировать через `MockEngine`.
- HTTP-поведение можно централизованно настраивать.
- Возможные альтернативы:
- Retrofit + OkHttp. Плюсы: зрелая Android-экосистема, много стандартных решений. Минусы: меньше унификации с multiplatform-friendly подходом, другой стиль описания API.
- Прямой OkHttp без абстракции клиента. Плюсы: максимум контроля. Минусы: выше объём низкоуровневого кода и хуже повторное использование настроек.

## ADR-010: Ошибки API нормализуются в `ApiOperationResult`

- Статус: Наблюдаемое/Действующее
- Контекст: Контрактные модули используют `ApiOperationResult`, а gateway переводят HTTP- и transport-ошибки в `Success`, `ValidationError`, `ApiError` и `NoInternet`.
- Решение: Использовать явную sealed-модель результата вместо проброса исключений в presentation-слой.
- Последствия:
- ViewModel работают с предсказуемыми состояниями через исчерпывающий `when`.
- Ошибки авторизации, валидации, сервиса и офлайна разделены единообразно.
- Обработка ошибок получается многословной, но поведение остаётся явным.
- Возможные альтернативы:
- Исключения до ViewModel. Плюсы: меньше обвязки в happy path. Минусы: сложнее добиться единообразной обработки и exhaustiveness.
- `Result<T>` + отдельные exception type. Плюсы: опора на стандартную обёртку. Минусы: хуже выражаются доменные варианты ошибок без дополнительных слоёв.

## ADR-011: `401 Unauthorized` централизованно очищает сессию

- Статус: Наблюдаемое/Действующее
- Контекст: `KtorGatewaySupport` очищает локальную сессию при HTTP 401 и только потом возвращает результат unauthorized.
- Решение: Считать отклонение backend-ом авторизации основанием для немедленной инвалидизации локальной сессии.
- Последствия:
- Устаревшие credentials удаляются единообразно.
- Фичи могут одинаково реагировать редиректом на onboarding/login.
- Политика сброса сессии задаётся в инфраструктуре, а не дублируется по фичам.
- Возможные альтернативы:
- Чистить сессию только в `app` после обработки результата. Плюсы: больше контроля в orchestration layer. Минусы: легко получить дублирование и непоследовательность.
- Пробовать silent refresh token. Плюсы: лучше UX. Минусы: нужна отдельная token lifecycle архитектура, которой сейчас нет.

## ADR-012: Управление состоянием через ViewModel и immutable UI state

- Статус: Наблюдаемое/Действующее
- Контекст: Feature ViewModel владеют mutable state и отдают экрану immutable data class-состояния через `copy`.
- Решение: Держать screen logic в ViewModel, а Compose-экран использовать как декларативный renderer состояния.
- Последствия:
- Валидация, загрузка, retry и преобразование ошибок живут вне composable-функций.
- UI остаётся декларативным.
- Переходы состояния удобно тестировать на границе ViewModel.
- Возможные альтернативы:
- Часть state logic держать прямо в composable. Плюсы: меньше классов для простых экранов. Минусы: хуже тестируемость и повторное использование логики.
- MVI/store-based подход. Плюсы: строгая модель событий и reducer-логика. Минусы: больше ceremony для текущего масштаба.

## ADR-013: Use case слой сохранён, хотя логика пока тонкая

- Статус: Наблюдаемое/Действующее
- Контекст: Feature-модули создают use case, которые в основном делегируют вызовы в gateway.
- Решение: Оставить слой use case даже там, где бизнес-логика пока минимальна.
- Последствия:
- Доменные действия имеют отдельные именованные точки входа.
- ViewModel не ходят в gateway напрямую.
- Часть use case сегодня является thin wrapper, что увеличивает число файлов, но поддерживает чистое разделение слоёв.
- Возможные альтернативы:
- Ходить из ViewModel напрямую в gateway. Плюсы: меньше файлов и абстракций. Минусы: presentation сильнее связывается с data contract.
- Полноценный domain/service слой с richer orchestration. Плюсы: лучше для сложной бизнес-логики. Минусы: сейчас это было бы преждевременным усложнением.

## ADR-014: Offline recovery реализован через общий экран отсутствия сети

- Статус: Наблюдаемое/Действующее
- Контекст: `AuthGraphState` хранит retry-callback и переводит пользователя на `NoInternetNavKey`, а `commonUiGraph` отображает общий экран с повтором действия.
- Решение: Обрабатывать offline-сценарии через единый navigation flow, а не через отдельные ad-hoc экраны в каждой фиче.
- Последствия:
- UX восстановления после потери сети единообразен.
- Фичи могут передавать отложенное действие повторной попытки.
- Для retry используется временный callback-механизм, а не полноценная надёжная очередь задач.
- Возможные альтернативы:
- Inline offline UI на каждом экране. Плюсы: больше контекстной гибкости. Минусы: сильное дублирование и расхождение UX.
- Глобальный banner/snackbar вместо отдельного экрана. Плюсы: менее навязчиво. Минусы: хуже подходит для blocking-сценариев загрузки.

## ADR-015: Matching использует optimistic UI и персистентную очередь действий

- Статус: Наблюдаемое/Действующее
- Контекст: matching-сценарий сразу продвигает карточки, локально сохраняет реакции и отправляет их на backend по очереди через `PendingMatchActionQueue` и `PendingMatchActionStore`.
- Решение: Приоритизировать непрерывный swipe UX, отвязав локальное действие пользователя от немедленного подтверждения сервером.
- Последствия:
- Свайпы остаются отзывчивыми даже при нестабильной сети.
- Непереданные реакции переживают process death.
- Приходится явно управлять порядком, retry и защитой от повторов.
- Возможные альтернативы:
- Ждать подтверждения backend перед переходом к следующей карточке. Плюсы: проще консистентность. Минусы: плохой UX при медленной сети.
- Использовать полноценную offline-first очередь через БД и worker. Плюсы: надёжнее доставка. Минусы: заметно сложнее инфраструктура.

## ADR-016: Небольшое локальное состояние хранится в SharedPreferences

- Статус: Наблюдаемое/Действующее
- Контекст: Сессия и pending match actions хранятся через SharedPreferences-базированные реализации.
- Решение: Для небольшого key-value и очередного состояния использовать лёгкое локальное хранение без Room или DataStore.
- Последствия:
- Реализация проста и быстра во внедрении.
- Для текущих размеров данных такой подход достаточен.
- Сложные запросы и эволюция схемы сознательно остаются вне текущего scope.
- Возможные альтернативы:
- DataStore. Плюсы: современный API, лучше асинхронная модель. Минусы: миграция и чуть больше инфраструктуры.
- Room. Плюсы: надёжнее для структурированных и растущих данных. Минусы: избыточно для текущих маленьких payload.

## ADR-017: Конкурентность в matching защищается явно

- Статус: Наблюдаемое/Действующее
- Контекст: matching orchestration использует `Mutex` во ViewModel для пагинации и дренирования очереди pending actions.
- Решение: Защищать критичные matching-сценарии через явную синхронизацию coroutine-потоков.
- Последствия:
- Исключаются параллельные повторные запросы пагинации.
- Pending reactions отправляются одной корутиной и в правильном порядке.
- Правила конкурентности остаются близко к orchestration-слою и не размазываются по UI и data-слоям.
- Возможные альтернативы:
- Надеяться на UI-дисциплину и флаги `isLoading`. Плюсы: проще код. Минусы: легко получить race condition.
- Вынести синхронизацию в repository/store слой. Плюсы: чище ViewModel. Минусы: потребуется дополнительная абстракция, которой сейчас нет.

## ADR-018: Debug network overrides встроены как инструмент разработки

- Статус: Наблюдаемое/Действующее
- Контекст: В debug-сборках приложение поддерживает shake gesture и отдельный экран для подмены API-ответов по endpoint.
- Решение: Встроить в приложение механизм локальной подмены ответов API для отладки и моделирования сценариев.
- Последствия:
- Edge case backend-а можно воспроизводить без серверных изменений.
- Отладка auth- и API-сценариев заметно ускоряется.
- Возможность намеренно ограничена debug-конфигурацией.
- Возможные альтернативы:
- Использовать только внешние mock-сервера. Плюсы: чище production code path. Минусы: медленнее настройка и сложнее локальная диагностика на устройстве.
- Не иметь override-механизма вовсе. Плюсы: меньше debug-кода. Минусы: хуже воспроизводимость проблем и сценариев деградации.

## ADR-019: Управление зависимостями через version catalog

- Статус: Наблюдаемое/Действующее
- Контекст: Версии зависимостей и plugin alias сосредоточены в `gradle/libs.versions.toml`.
- Решение: Управлять версиями библиотек и плагинов через Gradle version catalog.
- Последствия:
- Обновления зависимостей централизованы.
- Build script модулей короче и однообразнее.
- Снижается риск version drift между модулями.

## ADR-020: App-level orchestration вынесен в `TMatchAppState`

- Статус: Наблюдаемое/Действующее
- Контекст: По мере роста фич `TMatchApp` начал совмещать рендеринг оболочки, стартовый роутинг, back stack orchestration, FCM token sync, межфичевую координацию и обновление app-level UI state.
- Решение: Держать orchestration верхнего уровня в отдельном app-state/coordinator слое `TMatchAppState`, а `TMatchApp` оставить тонким composable, который в основном описывает layout и подключает графы.
- Последствия:
- Стартовая логика, tab navigation, profile-to-chat переходы, inter-feature feed actions и auth-bound app state сосредоточены в одном месте.
- `TMatchApp` проще читать и изменять, потому что он меньше похож на god composable.
- App-level состояние стало явнее и лучше отделено от декларативного UI.
- Возможные альтернативы:
- Оставить orchestration внутри `TMatchApp`. Плюсы: меньше файлов и абстракций. Минусы: рост связности и ухудшение читаемости корневого composable.
- Вынести orchestration в отдельную ViewModel. Плюсы: единый lifecycle-aware holder состояния. Минусы: для текущего масштаба это добавило бы лишний DI и ещё один слой между Compose и навигацией.

## ADR-021: Matching orchestration разделён между ViewModel и stateful interactor-классами

- Статус: Наблюдаемое/Действующее
- Контекст: `MainMatchingViewModel` управлял одновременно UI state, optimistic queue, дедупликацией рекомендаций, сборкой deck, удалением карточек и retry/drain логикой.
- Решение: Вынести изменяемую domain-adjacent orchestration-логику в отдельные классы `MatchingDeckCoordinator` и `PendingMatchActionQueue`, оставив ViewModel координировать use case, ошибки и публикацию `uiState`.
- Последствия:
- Логика формирования deck и дедупликации рекомендаций отделена от lifecycle/UI concerns.
- Очередь отложенных реакций и её синхронизация с persistent store инкапсулированы отдельно.
- `MainMatchingViewModel` стала короче и ближе к orchestration adapter, а не к хранилищу всей бизнес-механики фичи.
- Возможные альтернативы:
- Оставить всю механику в одной ViewModel. Плюсы: меньше классов и меньше DI wiring. Минусы: ухудшение тестируемости и высокая плотность ответственности в presentation-слое.
- Полностью увести orchestration в repository/service слой. Плюсы: ещё чище presentation. Минусы: пришлось бы расширять domain/data границы сильнее, чем это оправдано текущим размером фичи.

## ADR-020: Список чатов использует embedded карточку собеседника из chat preview контракта

- Статус: Принято
- Контекст: Обновлённый контракт `GET /chats/me` в `MVP Backend API Contracts.md` теперь отдаёт `other_user_card` вместе с `chat_id`, `other_user_id` и last message metadata. Unread counters и read status всё ещё отсутствуют.
- Решение: Строить список чатов напрямую из preview-ответа backend, использовать embedded `other_user_card` для имени и фото собеседника и хранить chat preview и chat messages в Room. UI подписывается на `Flow` из БД, сетевой refresh обновляет локальный кэш, а websocket `/chat/stream` пишет входящие сообщения в БД и обновляет `lastMessage` у чата.
- Последствия:
- Реализация остаётся строго в рамках существующего backend MVP-контракта и не придумывает несуществующие поля.
- Список чатов стал информативнее без дополнительной сетевой догрузки.
- При повторном открытии и кратковременной потере сети доступны последние закэшированные чаты.
- Экран самого чата догружает историю страницами вверх через `before_message_id`, при этом realtime-ивенты и HTTP-ответы сходятся в одной локальной модели данных.
- Для unread counters, read status и richer messaging UX потребуется дальнейшее расширение backend-контракта.

## ADR-020: Push-уведомления интегрированы через FCM с регистрацией device token на backend

- Статус: Наблюдаемое/Действующее
- Контекст: Приложение подключает Firebase Cloud Messaging, получает FCM token на устройстве и регистрирует его на backend через `POST /notifications/devices`. Контракт регистрации опубликован как `NotificationGateway` в `api/common`, а реализация живёт в `data/tmatch_api`. Оркестрация запускается из `app` при старте сессии и при refresh токена из `FirebaseMessagingService`.
- Решение: Использовать FCM как transport для push-сообщений, а backend-регистрацию токена встроить в существующую модульную схему через отдельный gateway-контракт и composition root в `app`.
- Последствия:
- Push-интеграция не ломает текущие границы между `app`, `api/*` и `data`.
- Регистрация токена выполняется только для авторизованной сессии и переиспользует общий Ktor/error handling стек.
- Обновление токена покрыто и на холодном старте, и при `onNewToken`.
- На текущем этапе входящие payload только логируются, без доменной маршрутизации и UI-обработки.
- Возможные альтернативы:
- Регистрировать token напрямую из `FirebaseMessagingService` без gateway-контракта. Плюсы: меньше файлов. Минусы: `app` начинает зависеть от transport-деталей и ломает модульные границы.
- Откладывать отправку token в отдельный worker/очередь. Плюсы: выше надёжность при офлайне. Минусы: заметно сложнее жизненный цикл и инфраструктура для текущего объёма задачи.
- Возможные альтернативы:
- Версии прямо в каждом `build.gradle.kts`. Плюсы: локальная явность. Минусы: дублирование и рассинхронизация.
- `buildSrc` или convention plugins для версий. Плюсы: мощнее кастомизация. Минусы: выше стоимость поддержки по сравнению с простым catalog.

## ADR-020: Архитектура частично защищена unit- и smoke-тестами

- Статус: Наблюдаемое/Действующее
- Контекст: В проекте есть тесты на стартовый роутинг, `AuthGraphState`, DI smoke resolution, поведение gateway и UI mapping.
- Решение: Проверять ключевые архитектурные контракты точечными unit- и smoke-тестами, а не полагаться только на UI/instrumentation.
- Последствия:
- Критичные flow и инварианты защищены с низкой стоимостью поддержки.
- Инфраструктуру можно тестировать без полноценного Android runtime.
- Покрытие избирательное, поэтому часть соглашений всё ещё держится на дисциплине команды.
- Возможные альтернативы:
- Делать упор в основном на instrumentation/UI тесты. Плюсы: проверяется реальное поведение end-to-end. Минусы: медленно, дорого и хрупко.
- Почти не тестировать архитектурные инварианты. Плюсы: меньше затрат сейчас. Минусы: выше риск регрессий в wiring и flow-логике.

## Правила зависимостей между модулями

Наблюдаемое направление зависимостей:

`app -> feature/* + api/* + data/tmatch_api + common/ui`

`feature/* -> api/* + common/ui`

`data/tmatch_api -> api/*`

`api/* -> api/common` там, где это нужно

`common/ui -> без зависимостей на другие project modules`

Это означает, что бизнес-контракты поднимаются из `api`, конкретные реализации приходят из `data`, а финальная сборка происходит только в `app`.

## Известные компромиссы

- Навигационные ключи в app back stack типизированы как `Any`, что даёт гибкость, но ослабляет compile-time safety.
- Обработка ошибок явная, но дублируется в нескольких ViewModel.
- Локальное хранение намеренно упрощено и, вероятно, потребует эволюции при росте offline-state.
- Этот документ описывает восстановленные по коду действующие решения, а не исходные исторические ADR с авторами и датами принятия.
