# Tmatch: карта критериев

Дата подготовки: 2026-03-17

## Назначение документа

Документ описывает соответствие текущей реализации `Tmatch` критериям оценки и указывает, чем каждый критерий подтверждается в коде или в проектной документации.

## Product

- `Ценность и завершённость CJM и выполняемых сценариев`
  Основной маршрут собран end-to-end: auth -> account profile -> dating profile -> matching -> профиль пользователя -> чаты -> сообщения. Подробно описан в [Описание функционала и статуса интеграции](./functional-overview.md) и [Тестовые сценарии](./test-scenarios.md).
- `Границы MVP и приоритезация фичей`
  В первую версию включены только auth, профиль, matching, чаты, push и диагностика. Границы и исключения явно перечислены в [Описание функционала и статуса интеграции](./functional-overview.md).
- `Приоритет базового сценария над второстепенными функциями`
  Дополнительные возможности, такие как debug-panel, локальный кэш и push, не заменяют основной сценарий, а поддерживают его устойчивость и диагностику.
- `Критерий успеха и проверяемые признаки результата`
  Проверяемыми результатами считаются успешная авторизация, сохранение профиля, загрузка колоды, выполнение действий над карточками, открытие чатов и отправка сообщений. Формализовано в [Тестовые сценарии](./test-scenarios.md).
- `Проверка критичных мест сценария`
  Отдельно покрыты offline, unauthorized, websocket degradation, ошибки контракта, debug overrides и push-сценарии. См. [Тестовые сценарии](./test-scenarios.md).
- `Пограничные сценарии использования`
  Документированы реакции на неизвестные backend значения, отсутствие сети, пустые чаты и отсутствие notification permission. См. [Тестовые сценарии](./test-scenarios.md).
- `Признаки ухудшения сценария`
  Признаками деградации считаются падение websocket до HTTP refresh, ошибки refresh чатов, offline-переходы, ошибки API и сбои регистрации push token. Для диагностики доступны логи и API overrides.
- `Продуктовое понимание ценности продукта`
  Продуктовая ценность и состав первой версии сформулированы в [Описание функционала и статуса интеграции](./functional-overview.md).

## Backend

- `Архитектура системы`
  Клиент разделён на `app`, `api/*`, `feature/*`, `data/tmatch_api`, `common/ui`, что фиксирует роли composition root, контрактов, UI и инфраструктуры. См. [ADR.md](../ADR.md).
- `Архитектура сервиса`
  В рамках этого репозитория реализован клиентский слой интеграции: gateway-интерфейсы опубликованы в `api/*`, concrete-реализации находятся в `data/tmatch_api`, presentation не зависит напрямую от транспорта.
- `Модель данных и переходы состояний`
  Сессия, стартовые переходы и chat cache оформлены явно. Разрешение стартового экрана описано в `AppStartDestinationResolver`, а ошибки API нормализуются в единый `ApiOperationResult`.
- `Проверка бизнес-логики и контрактов`
  Есть unit-тесты на мэппинг API-контрактов, стартовую навигацию, matching orchestration и сценарии чатов. В частности покрыты unknown enum/value cases и error mapping.
- `Безопасное добавление изменений без поломки сценария`
  Для smoke-проверки используется `./gradlew test`; сценарии, которые нельзя уверенно менять без регрессии, зафиксированы в [Тестовые сценарии](./test-scenarios.md).
- `Выпуск изменений и обновление схемы данных`
  Путь сборки прозрачен, но локальный чат-кэш пока использует `fallbackToDestructiveMigration`, что является текущим ограничением первой версии.
- `Наблюдаемость и диагностика сервиса`
  На клиенте реализованы просмотр логов приложения и ручная подмена ответов backend через debug-panel, что помогает диагностировать деградацию интеграции.
- `API и серверные контракты`
  Подключённые endpoints и сценарии использования собраны в [Описание функционала и статуса интеграции](./functional-overview.md). Важно: серверная часть в этом репозитории отсутствует, поэтому подтверждается именно качество клиентской интеграции и контрактов.
- `Архитектурные компромиссы и ограничения`
  Известные ограничения текущей версии перечислены в [Описание функционала и статуса интеграции](./functional-overview.md) и [ADR.md](../ADR.md): destructive migration, отсутствие unread/read receipts, частичный push e2e path.

## Mobile

- `UI/UX и навигация`
  Навигация собрана на app-level back stack с явными feature graph, стартовый экран зависит от состояния сессии и профиля, общий no-internet flow унифицирован.
- `Визуальная привлекательность`
  UI построен полностью на Jetpack Compose и общей дизайн-системе в `common/ui`, что обеспечивает единый визуальный язык между экранами.
- `Описание функционала и завершённость пользовательских сценариев`
  Описание функционала вынесено в [Описание функционала и статуса интеграции](./functional-overview.md), а пользовательские и краевые сценарии описаны в [Тестовые сценарии](./test-scenarios.md).
- `Тестовые сценарии`
  Подготовлен отдельный документ [Тестовые сценарии](./test-scenarios.md) с основными и краевыми пользовательскими путями, ожиданиями и полями для фактического прогона.
- `Работоспособность и баги`
  Проект проходит `./gradlew test`, имеет покрытие unit/UI tests для ключевых частей flow и использует единый слой error handling для сетевых и контрактных ошибок.
- `Производительность`
  Для matching используется optimistic UI, а для чатов локальный Room cache и Flow-подписка, что снижает зависимость UI от мгновенного ответа сети.
- `Обработка ошибок`
  Ошибки backend и transport-ошибки приводятся к `ApiOperationResult`, offline обрабатывается отдельно, `401` очищает сессию, а Android 13+ permission edge case учтён в push service.
- `Дебаг-панель и клиентская диагностика`
  В debug build доступны экран логов и экран подмены API-ответов, открываемые через shake gesture. Это покрывает диагностику и ручное тестирование нестабильных backend сценариев.
- `Сборка и запуск мобильного приложения`
  Проект собирается стандартным Gradle-путём. Актуальная автоматическая проверка: `./gradlew test` успешно выполнен 2026-03-17.
- `Общее качество контракта для мобильного приложения`
  Контракты ориентированы на мобильный сценарий: единый auth header flow, локальный чат-кэш, websocket для входящих сообщений, targeting/preferences отдельными endpoint, push token registration.
- `Обоснованность инженерных решений`
  Архитектурные решения, ограничения и компромиссы собраны в [ADR.md](../ADR.md) и согласованы с реальным состоянием кодовой базы.
